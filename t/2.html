LLMデータベース

Antigravityを活用して開発した、Worklog、Client、Invoiceの三つのプラグインは順調に動き始めたのですが、この手の機能をプラグインとして追加すると、「どのロールにどのプラグインをロードするか」が悩ましく、システム全体としての使い勝手が悪くなってしまいます。各ロールで使えるプラグインの数を増やすと、それに応じてシステムプロンプトの長さも長くなってしまうので、トークンの消費量も増えてしまうし、コンテキストが大きくなるとLLMとしての性能も落ちかねません。

そこでアイデアとして浮上したのが、汎用的なデータベース機能をファイルシステムの上に構築し、Worklog、Client、Invoiceのような機能は、その上に（専用のコードを書かずに）実装するというアイデアです。

別のところでもMulmoClaudeはDSL(Domain Specific Language)を活用していると紹介しましたが、ここでも同様に、データベースの上に専用のDSLを使ってWorklog、Client、Invoiceを実装すれば、（TypeScriptで実装された）プラグインなしで、それらの機能を追加することが可能になります。

この仕組みが実現できれば、MulmoClaude上で動くClaude Code自身にDSLを生成させることにより、将来的には、MulmoClaude自身がが自分の機能を拡張することが可能になります。

そこで、早速、(今度はClaude Codeを使って)汎用データベースをMulmoClaude上に構築することにしました。基本的にはWorklog、Client、Invoiceなど独自のスキーマ（データベース用語で用途ごとのデータ形式のこと。Worklogの場合だと、「働いた時間」「プロジェクト名」「顧客名」などをデータとして持ちます）を持ったデータの集まりをコレクション（Collection）と呼び、スキーマごとにClaude Code向けのスキル（Claude Codeに特定の仕事をさせる際に与えるプロンプト）を作ることにしました。

MulmoClaude側には、コレクションごとに定義されたスキーマを読み込んで、表示したり、ユーザーに編集をさせる汎用のUIがあり、LLMはスキーマを参照しながらスキルに書かれたプロンプトに従って、これらのデータを更新して行きます。

例えば、Worklogの場合だと、スキーマは以下の通りです。

```{
"title": "Worklog",
"icon": "schedule",
"dataPath": "data/worklog/items",
"primaryKey": "id",
"fields": {
"id": {
"type": "string",
"label": "ID",
"primary": true,
"required": true
},
"date": {
"type": "date",
"label": "Date",
"required": true
},
"clientId": {
"type": "ref",
"to": "mc-clients",
"label": "Client",
"required": true
},
"hours": {
"type": "number",
"label": "Hours",
"required": true
},
"billable": {
"type": "boolean",
"label": "Billable"
},
"notes": {
"type": "markdown",
"label": "Notes"
}
}
}
```

スキルの方は少し長いので割愛しますが、そこにLLMに向けたWorklog Collectionの活用方法が記述されています（参照：mc\-worklog/SKILL.md）。

興味深いのは、こんな単純な仕組みで、リレーショナル・データベースのようなことが出来てしまう点です。

WorklogにはclientIdというフィールドがありますが、それは、Clientコレクションのidと紐づいており、Worklog側に顧客情報を表示したり、特定の顧客向けのWorklogだけを抜き出したりすることが可能になっています。

実際に作っている過程で気がついたのですが、自然言語が理解できるLLMを使っているため、スキーマとして厳密に定義していなくても、文脈を読み取ってLLMが正しく処理してくれる点が、通常のデータベースとは大きく違います。

Worklogから特定の顧客向けの請求書を作る際には、「時給」が必須ですが、時給というフィールドがWorklogにもClientにもなくても、Clientのメモ欄に「時給：5000円」と書いてあれば、clientのデータを取得したLLMが文脈からそれ正しく読み取って、請求書を作成する際に活用してくれるのです。

従来型のデータベースでは、この手の情報はスキーマとしてきちんと定めておかなければ決してちゃんと動きませんでしたが、自然言語を理解できるLLMだからこそ、こんな柔軟なことができるのです。

ちなにみ、「時給：5000円」という書式が決まっているわけではないので、代わりに「時給は5000円」「単価：5000円/時」と書いても通じるし、必要に応じて「時給：2026年5月までは5000円、6月以降は6000円」のようなことを書いても、ちゃんと処理してくれる点は、従来型のデータベースよりもはるかに柔軟で優秀だとすら言えます。

この記事を書いている時点では、これらの機能はまだ開発中ですが、順調に進んでいるので、このメルマガが発行される頃には、MulmoClaudeの一部としてオープンソース化されているでしょうから、是非ともお試しください。
